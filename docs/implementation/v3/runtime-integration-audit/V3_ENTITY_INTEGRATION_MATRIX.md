## 3. Serialization, Validation & Schema Alignment Audit (`v3-storage-mappers.ts`)

1. **Strict Mapper Hygiene (Good in Isolation, Unconnected to Runtime):**
   - **Booleans:** [`booleanToSqlInt`](file:///D:/AI-COMPANY/company-mcp/src/db/v3-storage-mappers.ts#L425-L428) and [`sqlIntToBoolean`](file:///D:/AI-COMPANY/company-mcp/src/db/v3-storage-mappers.ts#L433-L446) reject non-booleans on write and reject integers other than `0`/`1` on read (fail-closed, tested in `t18`).
   - **JSON Fields:** [`parseJsonStringArray`](file:///D:/AI-COMPANY/company-mcp/src/db/v3-storage-mappers.ts#L451-L462) and [`parseJsonPlainObject`](file:///D:/AI-COMPANY/company-mcp/src/db/v3-storage-mappers.ts#L467-L473) fail closed on malformed JSON, `null`, primitives, or arrays where objects are expected.
   - **Nullable & Internal Fields:** `chat_messages.internal_metadata_json` (`v0.5.0-v3-foundation.sql:54`) and `room_audit_logs.internal_details_json` (`v0.5.0-v3-foundation.sql:110`) were synchronized with [`ChatMessage`](file:///D:/AI-COMPANY/company-mcp/src/db/v3-storage-mappers.ts#L555-L605) and [`RoomAuditLog`](file:///D:/AI-COMPANY/company-mcp/src/db/v3-storage-mappers.ts#L667-L706) during G2 hardening.
   - **Split-Table Atomicity:** [`knowledgeChunkFTSAdapter`](file:///D:/AI-COMPANY/company-mcp/src/db/v3-storage-mappers.ts#L1910-L1959) uses SQLite `SAVEPOINT` to write `knowledge_chunks_meta` + `knowledge_chunks_fts` atomically and detects partial orphans or duplicate FTS rows in `getById`.
   - **Timestamps:** All 25 V3 SQLite objects store ISO-8601 `TEXT` timestamps (aligned with G1 Zod contracts), intentionally diverging from [`03_DOMAIN_AND_DATABASE_DESIGN.md`](file:///D:/AI-COMPANY/docs/blueprint/v3/03_DOMAIN_AND_DATABASE_DESIGN.md#L496-L961) (`INTEGER` Unix epochs), though zero runtime service or Blueprint converter bridges the two models.
2. **Legacy Bypass Summary (Schema Coexistence Hazard):**
   - `v0.5.0-v3-foundation.sql` shares **0 table names** and **0 foreign keys** with [`schema-v050-rc2.sql`](file:///D:/AI-COMPANY/company-mcp/src/db/migrations/schema-v050-rc2.sql) (22 base tables + 1 FTS5 table).
   - For instance, `task_approval_bindings.task_id` references `project_tasks_v3(task_id)`, while runtime approvals sit in RC2 `approval_requests` linked to RC2 `tasks(task_id)` with **zero cross-sync**.
   - Similarly, `project_tasks_v3`, `agent_leases`, `review_assignments`, and `task_transition_logs` sit completely empty (`0` rows) while RC2 `tasks` and `task_events` mutate live production state.
   - Until Phase 2 service adapters add full CRUD (`update*`, `delete*`, `list*`, atomic transitions) and either migrate or bridge legacy RC2 tables under explicit Gate V3-G3 authorization, the entire V3 persistence layer remains an unreferenced library.
